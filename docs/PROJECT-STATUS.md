## 一、它是什么

一个**可运行的择偶定位评估系统**：用户填条件表单（可传照片），系统按博主「鳌烨（月老鳌烨）」的公开内容输出评分、择偶窗口、该放弃的幻想项与提升建议。

**它同时是一个「知道自己每句话有多少依据」的系统**——每条结论带证据强度标签，每份报告第一行是数据来源声明。

## 二、必须最先知道的四件事

### 1. 所有证据来自**同一家机构**

报告的**第一行**就是这句（不可折叠、随 API JSON 走）：

> 本系统的全部证据来自同一商业机构（鳌烨传媒）的公开内容。所有强度标签指的是「该机构内多个账号一致表述」，不代表跨机构或第三方独立验证。

**如果按「整个鳌烨矩阵 = 1 个来源」计算，159 条规则里没有一条是「已验证」的。** 这不是缺陷描述，是语料的事实。

### 2. 结论正确率**当前不可测**（这是结论，不是未完成项）

原因有两层：

| 层 | 说明 |
|---|---|
| **结构性错配** | 案例来自博主**口头问出来的条件**，产品需要用户**自填表单**——「博主不会问『你觉得自己情绪稳定度几分』」 |
| 分母为零 | 45 条案例平均缺 23/29 个必填项；严格口径下可评估案例 **0 条** |

**所以：不得对外声称任何准确率。** 此前出现过的 75.6% / 68.9% / 17.8% / 15.6% **全部撤回**。

### 3. 强度标签怎么读

| 标签 | 真实含义 | 能否进计算 |
|---|---|---|
| **机构内多源一致** | 该机构多个账号说法一致（**不是第三方验证**） | ✅ |
| **机构内 2 源一致** | 同上，2 个账号 | ✅ |
| **机构内单源** | 只有 1 个账号说过 | ❌ 只展示 |
| **外部可核验** | **你可以自己去查那个数据**（如国家统计局） | ✅ 不受账号数限制 |
| 外推参考 | 由相近人群规则外推，误差不可估计 | ⚠️ 显示但不进综合分 |
| 工程默认 | 无语料依据 | ❌ 不得进结论 |
| 体系参考 | 规则标记为仅供人工阅读 | ❌ 只展示 |

**报告里默认只显示绿/蓝/红三种标记；数量最多的「机构内单源」收在行尾「▸ 来源」里，点开可看完整依据。**

### 4. 这套语料**不能**支撑「对方的职业/长相/年龄/学历」具象画像（语料天花板）

**委托人和用户想要的是「对方画像」（职业身份、条件、长相）；这套语料里的最小构成单元是「门槛与排序」（你够不够格），不是「配对画像」（什么样的人配什么样的人）。这是本项目最重要的边界之一，不要当 bug 修。**

**证据链**（可复跑：node tools/portrait-coverage.mjs）
- 全量扫描 standards 94 条 + rules 159 条 + bands 9 条，抽出 **71 条**可能描述对方的候选；
- 逐条分类后，能当「对方条件」（target-attribute）的只有 **14 条**（画像配置里落成 11 条），其中 **8 条是家庭/资产维度**：门当户对 100%–200%（S-ASSET-006）、父母退休金（S-FAM-002）、家庭氛围（S-FAM-003 / R-DIM-023）、「条件好」三要素（R-DIM-020）、A7.2 登记口径（asset.a7）；
- 其余是底线行为（R-MATCH-006）、收入豁免（S-INCOME-003）和**按打分局名次 / 场次条件化的池子**（match.rank.* / event.*，需要用户先填名次或活动类型）；
- 语料里的颜值/身高/年龄标准全部是**对本人**或**需求侧排序**：S-LOOKS-001/006/011（本人标尺与核验）、S-HEIGHT-001/002/003（本人评分与「身高封顶颜值」）、S-MATCH-005/006/007（她/市场先看你什么）、S-MATCH-001/002/008（打分局名次→可达档位）、S-OCC-001/002（本人评分/编制）、S-AGE-*（活动级单条）。**没有一条是「什么条件的男生配什么条件的女生（含职业/学历/年龄/长相）」的描述段。**

**结论**：「职业/身份、身高/长相、年龄、学历、婚史、家庭结构」这些维度**给不出对方条件**；最多只能给方向（「对方/市场看重你什么」）或需求侧成本（要求独生 = 高要求）。报告里如实标注「语料没有口径」，不做编造。

**要突破需要补的语料**（按优先级）：
1. 博主直接做**配对描述**的段落：「这种条件的女生一般找什么条件的男生」，并给出职业/学历/年龄/外貌的类型或区间；
2. 对**对方**（而非本人）的显式门槛：对方年龄区间、学历线、职业类型、婚史接受度；
3. 场次**互选结果**数据（谁和谁配对成功 / 被谁拒绝）——唯一能反推画像口径的硬数据；
4. 对方侧**长相/形象**的类型偏好描述（现有全是本人标尺或需求侧链条转述）；
5. 家庭结构与婚史的**对方侧**口径（现在只当「你的要求成本」）。
工程侧另缺两个字段：生态位（黄金/白银/青铜）、期望对方独生——补了只解锁需求侧成本类，不解锁画像。

## 三、已知的局限（不要当成 bug，是已知事实）

1. **证据多样性受限于语料来源。** 100+ 个账号里绝大多数是同一批内容的矩阵分发。**V3 语料从 1511 条涨到 3533 条（3.5×），净提级 = 0 条。**
2. **40.3% 的语料是直播切片**（1424/3533，`aoye28` 自身占 71.5%）。**「有多少条视频说了某件事」反映的是切片密度，不是他说过多少次。**
3. **8 种「假独立」形式**中，**2 种确认无法自动检测**：
   - 同品牌**口头禅回响**（短句标签式跨 host 复用）→ 12-gram 抓不到，只能人工
   - **同稿轻改**（换词重录）→ 4-gram/2-gram Dice 正负分布重叠，**不建议自动判定**
4. **没有女生版硬件评分表**（找到了 3 个矩阵号复述，但及格线需 6 项、当前最多判定 4–5 项，且核心账号复述为 0）。女生侧用工程默认权重，已标注。
5. **语料有效时长约 76.7 小时**（78.2h 扣回音 47 分钟）。回音率 3.0%，**但没有任何一条被引用的引文落在回音区内**。
6. **场次识别有缺口**：`≤3h` 是代理；同一场直播在两号各切一段且内容不重叠的情况无法检测（需原始直播 ID）。
7. **主张分类缺一类**：「建议型/方法型」未覆盖，少量规则临时归入 `market-norm`（见 `OPEN-QUESTIONS.md`）。
8. **语料天花板：给不出「对方画像」。** 71 条候选里只有 14 条能当「对方条件」，且 8 条是家庭/资产——所以「职业/身份、身高/长相、年龄、学历、婚史、家庭结构」只有方向口径或没有口径（详见「二、4」与 `tools/portrait-coverage.mjs`）。

## 五、怎么让它变得更强（有标价的路径）

### 让「准确率」变得可测
| 做到哪一步 | 可评估案例 |
|---|---|
| 现状 | **0 / 45** |
| ＋ 表单允许 19 个自评/偏好项填「未知」（**已完成**） | 0 / 45 |
| ＋ 补语料 Top 12 字段 | **19 / 45** |
| ＋ 补 Top 14 字段 | **45 / 45** |

补的字段全是博主访谈里本就常问的（户籍/车/婚史/收入/院校/颜值自评/家庭出身/房/手足/学历/职业/身高/年龄/城市）。**这两步都不需要改引擎。**

### 让证据变强
只有一条路：**增加非矩阵来源**。同机构内部再怎么补语料，都只会增加同稿复述。

### 让女生侧对称
需 ①扩大表单字段（储蓄档/恋爱史/社保连续性）②裁定存款与恋爱史冲突 ③明确「正经工作」判定 ④争取核心账号权威复述。清单在 `knowledge/composite-criteria.female.md`。

## 八、这个系统的能力边界（一句话）

> 它**不能**告诉你「你值几分」。
>
> 它**能**告诉你——
> 这一句有 3 个账号说过、但都是同一家机构；
> 这一句只有 1 个人说过一次；
> 这一句的数字你可以自己去国家统计局查；

> 这一句是某场活动的报名门槛，不是市场规律；

### 推送前发现并解决的两个问题

1. **git 历史 2.47 GB**：来自 `refs/cindy/savepoints/*` 自动快照，内含 `data/audio/**/*.wav`
   （博主语音）。GitHub 单次推送上限 2 GB、单文件 100 MB，直推会失败且会公开音频。
   → **解法**：只推一个全新的单提交树（孤儿分支），不推历史。本地仓库保持原样。
2. **`git rm -r --cached .` 失败被 `2>/dev/null` 吞掉**，导致索引未清空、
   `.gitignore` 对已跟踪文件不生效，`dist/` 一度被暂存。→ 显式 `git rm -r --cached dist`。

### 环境注意
`github.com` 被解析到 `198.18.0.24`（保留地址段）——本机代理在做 fake-ip DNS 劫持，
GitHub 连接间歇性 `SSL_ERROR_SYSCALL`。所有 GitHub 操作需带重试。
